- DirectX / video-output selection. Root issue (also behind the Win11 crash):
  the engine's vout wrapper picks the display module from the "vout" variable,
  which this build never populates, so the search always ran as "any" and the
  highest-priority module that happened to initialise was used. Fix: the
  wrapper (VLCWORK/src/video_output/vout_wrapper.c, under RP_LEGACY) now chooses
  the module list by OS - "direct3d9,directdraw,rpgdi" on Windows 9x and
  NT 4/2000/XP, and "rpgdi" (software GDI) on NT 3.x and on Vista and later -
  honouring an RP_VOUT environment override that the front end's Video menu
  sets (rpgdi / directdraw,rpgdi / direct3d9,rpgdi / unset for Auto). libcore
  was rebuilt (ASMBLD) and re-stamped as LIBCORE.DLL. The DirectDraw and
  Direct3D9 plugins (with direct3d9_filters) are shipped again - 253 plugins -
  so DirectX acceleration is used where the OS provides it; Direct3D11 stays
  out (Vista+, and the Win11 crasher). On real 9x/2000/XP hardware with a GPU,
  direct3d9/directdraw open and accelerate; where they cannot (e.g. QEMU's
  Cirrus with no 3D), the chain falls back to RPGDI and plays. Verified on
  Windows 95: the log shows the preference honoured
  ("direct3d9,directdraw,rpgdi") and a clean RPGDI fallback.

Windows 11 playback crash fix (video output)
- Reported: on Windows 11 the player crashed during video playback
  (user TRACE.TXT + PLAYER.LOG). Root cause: the engine's vout wrapper selects
  the display module from the "vout" variable via the "$vout" expansion, but
  neither the global --vout=rpgdi option nor a per-item :vout=rpgdi media
  option sets that variable in this build, so the display search runs as
  "any". On the retro guests the hardware vouts (direct3d11/9, directdraw)
  cannot initialise, so "any" always resolved to the legacy RPGDI software
  output; on Windows 11 direct3d11 (capability 300) initialises and wins over
  RPGDI (100), and that Direct3D path - never exercised by this i386/no-SIMD
  legacy build - crashes mid-playback (PLAYER.LOG ends right after the D3D11
  device is created and the first re-buffer).
- Fix: the hardware and non-legacy video outputs are no longer shipped -
  direct3d11, direct3d11_filters, direct3d9, direct3d9_filters, directdraw and
  wingdi were removed from BIN/PLUGINS and the installer plugin set (250
  plugins now, from 256). RPGDI is left as the only general "vout display"
  module, so "any" resolves to RPGDI deterministically on every system,
  including Windows 11, matching the design (the legacy GDI output is the
  renderer). The frontend also now requests ":vout=rpgdi" per item and keeps
  --vout=rpgdi as belt-and-suspenders. BIN/PLUGINS/PLUGINS.DAT was dropped so
  the reduced set is rescanned on first run (RETRO.EXE already resets the
  cache when it is absent).
- Verified on Windows 95 under QEMU with the reduced set: RETRO.EXE rescans
  the plugins, the user's 720p H.264+AAC MP4 plays, decoded frames render, the
  log shows "using vout display module RPGDI" with no plugin-load errors, and
  the guest exits cleanly. Windows 11 cannot be exercised in this environment;
  the fix removes the crashing D3D11 path entirely and forces the GDI output
  that is fully supported on Windows 11, so the user should re-test there.
